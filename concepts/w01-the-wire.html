Layer 2 — ChapterThe mechanism

2  What HTTP actually is

HTTP is a request/response protocol over a reliable byte stream. That's the whole thing. TCP gives you an ordered stream of bytes with no message boundaries; HTTP's job is to impose boundaries on that stream and attach meaning to what's inside them.

Everything else — routing, controllers, serialisation, middleware — is code someone wrote on top of that. When you build RequestParser this week, you are writing the layer that every framework you will ever use is standing on.

2.1  Anatomy

A request has exactly four parts, in order:

PartFormatTerminated by
Request lineMETHOD SP target SP HTTP/versionCRLF
Header fieldsname: value, one per lineCRLF each
Empty linenothingCRLF
Bodyopaque bytesframing rules — see §2.3

The line terminator is CRLF — carriage return then line feed, bytes 0x0D 0x0A. Not \n. This trips people constantly because most editors and most Java string handling default to \n, and a server that accepts bare \n will happily parse a request that a strict server rejects. Worse, the discrepancy is the mechanism behind request smuggling attacks, where a proxy and an origin server disagree about where one message ends and the next begins.

2.2  Headers are trickier than they look

Three things that will bite you when you write Headers.java:

Field names are case-insensitive. Content-Type, content-type and CONTENT-TYPE are the same field. HTTP/2 goes further and requires lowercase on the wire. Your map must not be a plain HashMap<String,String>.

Split on the first colon only. Values contain colons routinely — timestamps, URLs, IPv6 addresses. line.split(":") is a bug waiting for a Date header.

A field can appear more than once. Repeated fields are semantically equivalent to one field with comma-joined values — but only for fields whose grammar is a comma-separated list. Set-Cookie famously breaks this rule, which is why it needs special handling in nearly every HTTP library ever written.

2.3  Message framing

The server reads the request line and headers up to the empty line. Then it must decide how many body bytes to read. The rules, in priority order:

1. Transfer-Encoding: chunked wins. The body arrives as a sequence of chunks, each prefixed by its size in hexadecimal, terminated by a zero-length chunk. This lets a sender stream a body whose total length it doesn't know yet.

2. Otherwise Content-Length decides. Read exactly that many bytes. Not one more, not one fewer.

3. Otherwise there is no body. For a request, absence of both headers means zero-length body. (Responses have an extra rule: they may be framed by connection close, which requests cannot use — the server would have no way to reply.)

If both headers appear, that is a framing ambiguity and a security problem, not a puzzle to resolve cleverly. Reject the message.

Why this matters beyond parsing

Connections are reused. After one request/response cycle, the same TCP connection typically carries the next request. If your parser reads one byte too few, those leftover bytes become the start of what looks like the next request — attacker-controlled bytes interpreted as a request line. That is request smuggling, and it is a framing bug, not a fancy exploit.

2.4  Statelessness

HTTP is stateless in a precise sense: each request carries everything the server needs to understand it. The server is not required to remember anything between requests.

Note what this does not say. It does not say the application has no state — your quotes obviously persist. It says the protocol carries no state. Session state is application state, and if you keep it server-side you have made a deliberate trade: you gained revocability and lost the ability to route any request to any instance without coordination.

Hold that sentence. In Week 12 you will make exactly this trade again under the name "sessions versus JWT," and most people make it badly because they never connected it back to here.

2.5  Connection lifecycle

In HTTP/1.1 connections are persistent by default. One TCP connection, many request/response pairs, in order. Connection: close opts out. This is why your server can't just read everything until EOF — EOF may never come.

Requests on one connection are strictly ordered: response 1 must be fully written before response 2 begins. HTTP/1.1 pipelining tried to overlap this and failed in practice because of head-of-line blocking, which is one of the problems HTTP/2 multiplexing was built to solve. You are implementing 1.1, so: one at a time, in order.

Layer 3 — ProofAnswer before revealing

3  Self-test

Write your answer down first. Recognising a correct answer is not the same as producing one, and the gap between those two is exactly where week-one confidence goes to die.

Q1
Your parser reads headers with line.split(":") and takes index 0 and 1. Name a real header this breaks, and say what the broken value looks like.

Date: Tue, 18 Aug 2026 09:14:22 GMT — you'd get the value " Tue, 18 Aug 2026 09" and silently drop the rest. Same for Location with an absolute URL (https://…) and any IPv6 host. Split on the first colon: indexOf(':'), then substring.

Q2
A request arrives with Content-Length: 61 but the client sends 61 bytes of body and then immediately sends a second request on the same connection. Walk through what your server reads. Now change it to Content-Length: 55. What does the server see as the start of the next request?

With 61 it reads exactly the body, leaves the buffer positioned at the start of request two, and the next parse works. With 55 it reads 55 bytes, leaves 6 body bytes unread, and then tries to parse those 6 bytes as a request line. Best case: 400. Worst case: those bytes are attacker-chosen and form a valid request line, and you have just executed a request the client never legitimately sent.

Q3
Why can a response be framed by closing the connection, but a request cannot?

Because the connection is bidirectional and the roles are asymmetric. A server that has finished writing a response can close and the client knows the body ended. A client that closed to signal "body finished" would have destroyed the channel the response needs to come back on.

Q4
HTTP is stateless. You are about to build a login. State one thing that fact permits and one thing it costs you.

Permits: any request can be handled by any server instance, so you scale horizontally without sticky sessions or shared session storage. Costs: identity must be re-established on every single request, which means credentials or a token travel on every request — more surface area, more to validate, and a revocation problem if you push that state entirely to the client.

Q5
Your Headers class is a HashMap<String,String>. Give two distinct bugs this causes.

(1) Case sensitivity — a client sending content-type gets a null lookup for Content-Type, so your negotiation silently fails. (2) Repeated fields — the second occurrence overwrites the first, so Accept-Encoding: gzip followed by Accept-Encoding: br loses gzip. And a third, if you want it: no ordering guarantees for fields where order carries meaning.

Q6
A message arrives with both Content-Length: 10 and Transfer-Encoding: chunked. What do you do, and why is "prefer chunked and move on" not good enough?

Reject it — 400, close the connection. "Prefer chunked" is what the spec says a recipient should do if it processes the message at all, but the danger is that you are rarely the only hop. If a front proxy honours Content-Length and you honour Transfer-Encoding, the two of you disagree about where the message ends, and the difference is a smuggled request. Ambiguous framing is refused, not resolved.
