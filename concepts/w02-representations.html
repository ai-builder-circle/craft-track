Representations

A resource is a concept. A representation is a rendering of it, at a moment, in a format. Confusing the two is why most APIs return 200 with an error inside the body.

2  Resource, representation, and why it matters

Fielding's definition: a resource is any concept that can be identified — a quote, the set of quotes for a client, "today's exchange rate." A representation is a concrete byte sequence describing that resource's state at a point in time, in some format.

The URL identifies the resource. The Content-Type describes the representation. One resource can have many representations: the same quote as JSON, as CSV, as a PDF, in English or Afrikaans. They are the same resource, so they share a URL, and the client says which rendering it wants via Accept.

This matters practically because it tells you what belongs in the URL and what does not. /quotes/9f3a?format=json is putting representation choice into resource identity. It works, plenty of APIs do it, and it means your cache now has two entries for one resource. Use the headers; they exist for this.

2.1  Negotiation mechanics

The Accept header is a list of media ranges with quality weights:

Accept: text/csv, application/json;q=0.8, application/xml;q=0.3

Rules that catch people out:

Absent q means q=1.0. In the header above, CSV is the client's first choice even though it's written without a weight — a lot of people read left-to-right and assume JSON wins because it has the visible number.

Specificity breaks ties, weight does not. application/json beats application/* beats */* at equal q.

q=0 means "not acceptable." It is an explicit veto, not a low preference. application/json;q=0 forbids JSON.

You choose, not the client. Negotiation is a preference expression. If the client's top choice is expensive and its second is cheap, you may serve the second — you just have to say which one you sent, in Content-Type, and add Vary: Accept so caches don't serve the CSV to the next client who wanted JSON. Forgetting Vary is one of the most common caching bugs in production APIs.

Accept vs Content-Type

They point in opposite directions and both can appear on the same message. Content-Type describes the body attached to this message. Accept describes what the sender wants back. A POST carries both: "here is JSON, send me back CSV." Get these confused and you will return 415 when you meant 406.

2.2  Status codes as a decision procedure

Five classes. The first digit is the contract; the rest is detail.

ClassMeaningWho is at fault
1xxInterim — keep waitingNobody
2xxUnderstood and acted onNobody
3xxFurther action needed to completeNobody
4xxThe request was wrongThe client — retrying unchanged will fail again
5xxThe request was fine, the server failedThe server — retrying may succeed

That last column is the whole point. A client's retry logic reads the first digit and decides whether to give up or back off and try again. When you return 500 for a validation failure, you have told every well-behaved client in the world to retry a request that can never succeed. When you return 200 with {"error": "not found"}, you have told caches to store the error and monitoring to record a success.

The 400 vs 422 argument — have a position

422 originates in WebDAV, not core HTTP. One camp says syntax errors are 400 and semantic errors are 422; the other says 400 covers both and 422 adds nothing a client acts on differently. Both are defensible. What is not defensible is using them inconsistently within one API. Pick one, write ADR-002, and I will ask you to defend it at the gate — I don't care which you chose, I care that you chose.

2.4  401 and 403 are not "not logged in" and "no permission"

The names are historically bad. 401 Unauthorized actually means unauthenticated: I don't know who you are, or the credentials you gave are wrong. It is required to carry WWW-Authenticate telling the client how to authenticate. 403 Forbidden means I know who you are and the answer is still no; retrying with the same identity is pointless.

The interesting case is when a resource exists but this user may not know that it exists. Returning 403 leaks existence — an attacker enumerating /quotes/{id} learns which IDs are real. Returning 404 hides it. Both are correct HTTP; it is a security decision, not a protocol one, and you will make it deliberately in Week 13.

2.5  Error bodies: RFC 9457 Problem Details

The status code tells a machine what class of thing went wrong. It cannot tell a developer which field was invalid. That's what the body is for — and there is a standard so you don't invent your own shape.

HTTP/1.1 409 Conflict Content-Type: application/problem+json { "type": "https://api.freelanceforge.co.za/problems/quote-not-editable", "title": "Quote cannot be edited", "status": 409, "detail": "Quote QF-2026-0184 was sent on 2026-08-14 and is no longer editable.", "instance": "/quotes/9f3a", "quoteStatus": "SENT" }

Note the media type: application/problem+json, not application/json. That's how a client knows to parse it as a problem rather than as your normal payload.

Field discipline: type is a stable URI identifying the kind of problem — it is the thing clients branch on, so it must never change. title is a human summary for that type and stays constant. detail is specific to this occurrence and may vary. Extension members (quoteStatus above) are allowed and are where you put machine-usable specifics.

What never goes in a problem body

Stack traces. SQL. Internal hostnames. Class names. Framework versions. Whether a username exists. Every one of those is reconnaissance, and 5xx handlers leaking them are one of the most reliably productive things a penetration tester checks. Log the detail, return the reference: "detail": "Internal error. Reference: 7f2a-9c11."

Layer 3 — ProofAnswer before revealing

3  Self-test

Q1
A client POSTs a line item to a quote that has already been sent. Your domain refuses. What status, and why not 400?

409 Conflict. The request was perfectly well-formed — correct syntax, valid fields, existing resource. Nothing about the request needs fixing. What's wrong is the state of the resource, which the client could not have known and might not be able to change. 400 says "your message was broken." 409 says "your message was fine, the target isn't in a state that permits it." A client can act differently on those: re-read the quote and show the user its status.

Q2
Accept: text/csv, application/json;q=0.8. Your server can produce both, but CSV generation takes 4 seconds and JSON takes 20ms. What may you legitimately do, and what must you send if you do it?

You may serve JSON. Negotiation expresses preference, not obligation — the client said it accepts JSON at 0.8, so JSON is acceptable. You must set Content-Type: application/json so the client knows what it got, and you must set Vary: Accept so a shared cache doesn't hand this JSON response to the next client who asked for CSV only.

Q3
Distinguish 406 and 415 in one sentence each, then give a single request that could plausibly trigger either.

415: I cannot consume the body you sent me. 406: I cannot produce anything you said you'd accept.

One request triggers both possibilities: POST /quotes with Content-Type: application/xml and Accept: application/pdf, on a server that speaks only JSON. Check the inbound first — 415, because you can't even read the request, so there's no point negotiating a response you'll never generate.

Q4
Your 404 handler returns {"error":"Quote not found"} with Content-Type: application/json. Name two things wrong with this, protocol-wise.

(1) The media type should be application/problem+json — a client cannot distinguish an error body from a normal payload by content type alone, so generic client code has to branch on status and then guess at the shape. (2) The body is an ad-hoc structure with no type URI, so clients must string-match on error text to branch. The moment you rephrase that message, every client breaks. A stable type URI is the contract; prose is not.

Q5
DELETE succeeds. Should you return 204 or 200 with the deleted representation? Argue both, then commit.

204: the resource is gone, there is nothing to represent, and returning the corpse invites clients to depend on it. Cheapest, cleanest. 200 with body: useful when deletion is soft, or when the client needs the final state for an undo affordance or an audit display, saving a round trip.

Either is defensible. The wrong answers are 200 with an empty body (lying about having a representation) and 204 with a body (a protocol violation — some intermediaries will strip it and some clients will hang). Write it in the ADR.

Q6
Why must 201 carry Location and 405 carry Allow? What breaks without them?

Location on 201: the client asked you to create something and does not know its identity — the server assigned it. Without Location the client must guess the URL or re-query a collection to find what it just made. It's the only way to learn the identifier reliably.

Allow on 405: you've told the client "not that method" without saying which methods work, so the only recovery is brute force. Allow: GET, PUT, DELETE turns a dead end into a correction. Both are required by the spec, not conventions.
