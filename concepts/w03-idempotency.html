Idempotency & Conditional Requests

Layer 2 — ChapterThe mechanism

2  Two properties that decide whether retries are safe

These two words get used loosely and they are not the same thing. Precision here is the difference between an API that survives a bad network and one that double-charges people.

MethodSafe?Idempotent?Meaning
GETyesyesRead only, no intended effect.
HEADyesyesLike GET, headers only.
PUTnoyesReplace. Doing it twice lands in the same state.
DELETEnoyesRemove. Second delete finds it already gone.
POSTnonoNo guarantees. This is why POST is dangerous to retry.
PATCHno*Not idempotent in general — depends on the patch.

Safe means the request has no intended effect on server state. The client is asking a question, not issuing an instruction. Safe methods can be prefetched, cached, and retried without a second thought.

Idempotent means making the request N times has the same effect on server state as making it once. It says nothing about the response — DELETE may return 204 the first time and 404 the next — it's about the resulting state. This is the property that makes automatic retry safe.

The one that trips everyone

Every safe method is idempotent, but not every idempotent method is safe. PUT and DELETE change state (not safe) yet repeating them changes nothing further (idempotent). Reading state has no effect (safe) and therefore trivially can't have a different effect when repeated (idempotent). The reverse containment doesn't hold, which is the whole subtlety.

2.1  Why POST is the problem child

POST means "process this according to the resource's own semantics" — the loosest contract in HTTP. "Add a line item" creates a new line item each time. So the retry-after-lost-response scenario from the lab creates duplicates, and the client can't tell the difference between "it failed, retry" and "it worked but the acknowledgement got lost."

2.2  The idempotency key pattern

Core HTTP gives you no way to make POST idempotent. The industry convention — popularised by Stripe, now near-universal for payments — is a client-supplied key:

POST /quotes/9f3a/line-items Idempotency-Key: 4f21c8de-77b0-4c1a-... Content-Type: application/json {"description":"Logo concept round","amountCents":450000}

The server keeps a store keyed by that value. First time it sees the key: do the work, store the response against the key, return it. Any later request with the same key: skip the work entirely, return the stored response. The client can now retry a payment as many times as the network forces it to, and exactly one line item is created.

Three things that make this correct rather than merely plausible, and that I'll ask about at the gate:

You store the response, not just a "seen" flag. A retry must get the same answer, including the created resource's ID. A bare "already processed" reply is useless to the client.

Keys expire. You cannot keep every key forever. Pick a window (24–72h is typical) that comfortably exceeds any client's retry horizon, and document it.

Concurrent duplicates race. Two retries can arrive before the first finishes. You need a lock or an atomic insert on the key, or both requests do the work. This is the hard part, and it's why the naïve version is subtly broken.

2.3  Conditional requests: making state changes safe against each other

Idempotency protects against your own retries. Conditional requests protect against other people's concurrent edits — the lost update from the lab.

An ETag is an opaque validator the server attaches to a representation — a version fingerprint. Change the resource, change the ETag.

GET /quotes/9f3a → 200 OK ETag: "v7" PUT /quotes/9f3a If-Match: "v7" ← "only apply this if the quote is still at v7"

If the resource still matches, the write proceeds and the ETag advances. If someone else already wrote — moving it to "v8" — the precondition fails and the server returns 412 Precondition Failed. The second writer is forced to re-read, see the other person's change, and decide what to do, instead of silently clobbering it.

HeaderQuestion it asksTypical use
If-MatchIs it still this version?Safe updates — 412 if not
If-None-MatchIs it not any version I hold?Caching — 304 if unchanged
If-Modified-SinceChanged since this time?Weaker, time-based caching

2.4  Caching and the 304

The same ETag machinery drives caching from the other direction. A client that already holds "v7" sends If-None-Match: "v7" on its next GET. If nothing changed, the server returns 304 Not Modified with no body, and the client reuses what it has. You save the payload; the validation round-trip still happens.

Cache-Control governs whether a round-trip is needed at all: max-age lets a client skip revalidation for a while; no-cache forces revalidation every time (note: it does not mean "don't store"); no-store is the one that means don't keep it. Getting these three confused is why sensitive data ends up in a proxy cache.

2.5  PUT vs PATCH, and JSON Merge Patch

PUT replaces the whole representation. Omit a field and you've set it to absent — PUT is not partial update, and treating it as such silently deletes data. PATCH applies a change description. The most common format is JSON Merge Patch (RFC 7386): send only the fields you're changing; null means "remove this field."

PATCH /quotes/9f3a Content-Type: application/merge-patch+json {"clientNote": "Rush job", "discountCents": null} ↑ set the note ↑ remove the discount

The trap in Merge Patch: because null means delete, it cannot represent "set this field to the JSON value null." For most domains that's fine. When it isn't, you need JSON Patch (RFC 6902) instead, which is more powerful and much fiddlier. Know that the choice exists.

2.6  Pagination — offset breaks under writes

Collections need paging. The obvious way — ?offset=40&limit=20 — has a real bug: if a row is inserted or deleted while a client pages through, the offset shifts under them, so they skip a record or see one twice. Fine for a static report, wrong for a live list.

Cursor pagination fixes it: the server returns an opaque cursor pointing at "the row after this stable key" (a timestamp-plus-id, say), and the client asks for "the next 20 after this cursor." Inserts and deletes elsewhere in the collection no longer disturb the client's position. Deliver the cursor as a Link header (RFC 8288) with rel="next", so paging is discoverable rather than something clients hand-assemble.

Layer 3 — ProofAnswer before revealing

3  Self-test

Q1 — the gate question
Two clients GET the same quote, both see ETag "v7", both edit, both PUT with If-Match: "v7". Walk through exactly what each receives, and what state the quote ends in.

Client A's PUT arrives first. The quote still matches "v7", so the write applies and the ETag advances to "v8". A gets 200 (or 204).

Client B's PUT arrives second, still carrying If-Match: "v7". The quote is now at "v8", so the precondition fails: B gets 412 Precondition Failed and its write is rejected. B must re-GET, see A's change at "v8", reconcile, and retry with the fresh ETag. The final state contains A's edit and B was prevented from silently overwriting it — which, without If-Match, is exactly what would have happened. This is the answer you carry into Week 9; the version column does the same job in the database.

Q2
Your idempotency store keeps only a set of "keys already seen." A payment POST is retried after its response was lost. What does the client get, and why is it not good enough?

The server sees the key, knows it's a duplicate, and returns something like 409 or an empty 200 — but it cannot return the original result, because it never stored it. The client wanted the created line item's ID and the original status. It now has neither, and can't tell whether the first attempt truly succeeded. You must store the full response against the key, so a retry is indistinguishable from getting the original reply.

Q3
Is PUT idempotent? Is a PUT that sets a field to serverTimestamp = now() idempotent? Reconcile the two answers.

PUT is defined as idempotent — the method contract promises it. But idempotency is about the effect the client intends to cause, i.e. replacing the resource with the representation the client supplied. If your handler injects now() on every call, you have added a side effect the client did not request, and repeated PUTs land in different states. The fix is not "PUT isn't idempotent" — it's "don't put non-deterministic server-side effects in an idempotent handler." Server-assigned values like timestamps belong to creation, or should be derived deterministically, not stamped on every replace.

Q4
A client sends PUT /quotes/9f3a with a body containing only {"clientNote": "urgent"}, intending to add a note. The quote had five line items. What happens, and which method did they want?

PUT replaces the entire representation. The body has no line items, so a correct server sets the quote to have no line items — five items deleted, silently, by someone who thought they were adding a note. They wanted PATCH with a merge-patch body {"clientNote":"urgent"}, which changes only the named field. This is the single most common data-loss bug caused by misunderstanding PUT, and it's why "PUT for partial update" must fail review.

Q5
Cache-Control: no-cache — does it mean "do not cache this"? If not, which directive does?

No. no-cache means "you may store it, but you must revalidate with the origin before every reuse" — a 304 round-trip. The directive that actually means "do not keep a copy at all" is no-store, and that's the one you want for anything sensitive. The naming is genuinely misleading and it's a routine source of leaked private data sitting in an intermediary cache.

Q6
Why does offset pagination skip or duplicate rows under concurrent writes, and how does a cursor avoid it? Give the concrete failure.

Offset counts positions, not rows. A client reads rows 1–20 (offset=0), then asks for offset=20. If a new quote is inserted at the top in between, every row shifts down one, so the row that was at position 20 is now at 21 — the client's offset=20 re-reads position 20, which is now the old row 19, a duplicate. A deletion causes the mirror-image skip. A cursor anchors to a stable key ("everything after created_at=…, id=…") rather than a position, so inserts and deletes elsewhere don't move the client's anchor. Position is relative; a key is absolute.
